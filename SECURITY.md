# Launcher security model

The modern local shell uses Electron 44.7.0 / Chromium 152. The separate original Flash host uses Adobe Flash 32.0.0.363 and Electron 11.5.0 / Chromium 87. Flash and that legacy Chromium remain unsupported with unresolved vulnerabilities. This launcher cannot claim to fix all vulnerabilities in those binary runtimes. npm audit covers npm dependencies only.

The projector/AppContainer migration is an unshipped prototype. Actual OS containment tests and an owned AS3 settings/render fixture pass, but Flash shared-object persistence fails. The production launcher still uses the existing game host; the shipped launcher must not be described as a completed projector migration or a fix for Flash CVEs. See docs/PROJECTOR.md.

## Trust boundaries

- The shell loads only six allowlisted local UI/code/brand assets under blitz://app/. It has a strict content-security policy, Chromium sandbox, context isolation, no remote Node integration, no webviews and no downloads or external navigation. No general browsing view, listener/socket bridge or remote tabs remain.
- IPC accepts launcher actions only from the exact shell WebContents/main frame at blitz://app/index.html. Browser actions are gone. Settings fields are independently validated in the main process; DOM fields are not a trust boundary.
- One separate sandboxed Flash session receives its selected game URL through its launch environment. The URL is validated again there. Its HTTP requests stay within the parsed selected origin; cross-origin redirects, game-host popups and downloads are denied. Clicked game links reload the configured game page. External HTTP/HTTPS links require Chromium user activation and go through the modern main process to the default browser, with independent scheme/credential validation and burst suppression. HTML clicks are observed in a separate isolated world, with event.isTrusted and the exact binding context checked; the binding is not present in the game page's world. Flash popup requests use Chromium's reported user gesture. Remote content receives no external-opening API. Tests replace browser handoff with an in-memory recorder before any OS launch. HTTPS is required except explicitly local HTTP addresses. No certificate overrides or insecure-content switches are enabled.
- Raw Flash TCP sockets are NOT filtered by HTTP origin restrictions. A selected server can run untrusted Flash content inside an obsolete runtime. Use a trusted game server; URL validation is not proof of trust. No credentials are extracted and no game content gets a preload or Node/Electron remote API.
- Runtime command transport is a random named pipe with a per-launch random authentication token. Both ends limit messages to 32 KiB while bytes arrive, before a newline or JSON parsing, and reject malformed/nonobject envelopes and failed handlers. The owner caps simultaneous connections at eight and expires unauthenticated connections after five seconds. These bounds reduce memory exhaustion and malformed-message crashes; they do not contain an already compromised privileged host. Environment tokens are not written to diagnostics. Tests using injected input/captures and dummy paste are enabled only in unpackaged test launches, not through the production shell IPC.
- Game and native-controller children inherit an allowlist of Windows/profile path and locale variables plus their explicit per-launch settings. API tokens, SSH-agent endpoints, signing variables and Electron/Node debugging configuration are not copied from the parent's environment. Tests verify this with dummy secrets and exercise the actual runtime after filtering. This prevents accidental environment exposure; it does not stop a native sandbox escape from accessing files/resources permitted to the Windows user. Profile locations remain unchanged, preserving the existing sign-in/session.
- A native helper owns and positions only the provided game HWND. The game keeps its native Chromium activation/input queue. Fullscreen marks the game HWND through the Windows Shell API; there is no global taskbar hiding or persistent topmost mode.
- A small Node-API module loaded only by the trusted legacy main process subclasses that process's game HWND on its owning thread. It accepts only a native handle buffer for a window in the current process/current thread; it never injects into another process. Inside the game rectangle it returns HTCLIENT and denies move/size system commands, removing Chromium's stale frameless border. Normal Flash input remains native. Subclass removal occurs on window destruction and environment cleanup. No new game-page API, pointer hook or cursor operation is exposed. Electron's movable/resizable policy is disabled; trusted launcher size requests briefly update its constraints on its own window thread while the subclass continues blocking interactive resizing. NativeHost positions the window without a competing size mutation.

## Client presentation compatibility

The legacy main process uses its in-process DevTools Fetch response interception for DungeonBlitz.swf on the selected origin. It opens no debugging port, proxy or new listener. HTTPS navigation, certificates, cookies and the SWF's original security origin remain in use. Response bytes must match a reviewed SHA-256 before decompression or editing; decompressed length and the two method hashes are checked again. Unknown revisions continue unchanged and the local settings panel reports the compatibility limit.

The presentation patch changes Main.method_561 picture layout/centering/clipping and class_71.method_1156 Lost Focus splash presentation. Original input listeners, actual focus state and key cleanup, authentication, packets, assets and game data remain intact. Flash covers the whole viewport so its own native mouse handling receives side-margin clicks and coordinates; there is no global mouse hook or synthetic gameplay click forwarding. No SWF is included in the distribution. Tests reconstruct the original bytes outside those two methods and their length fields, inspect decompiled output, and exercise the live client and an isolated Flash stage fixture.

## Client audio adapter

A launcher-owned BlitzAudio class is compiled in a separate ABC tag against the reviewed client definitions. Existing bytecode is not decompiled and recompiled. Relocation-aware insertions add channel gain tracking in five SoundManager methods and surround 21 existing sound calls with emitter/category context. The build checks expected call/assignment counts, valid branch/exception offsets and byte-identical code for the other 3,746 original method bodies. Authentication, packets, inventory, entity state and gameplay formulas are untouched. The fetched SWF is not bundled: a bounded delta is applied after the original exact-hash presentation check, with hashes for both the input and reconstructed output. Damaged or unsupported deltas fall back to the presentation-only client, with categories unavailable.

The game receives two Flash ExternalInterface callbacks limited to audio: four integer 0–100 category levels and an audio-only diagnostic snapshot. No Node, Electron, account or outbound-launch API is added. Only validated local settings reach the host command pipe; each side validates the values. Channels use weak keys and completion cleanup. Existing streams run their original fade step against their original gain before category attenuation is reapplied, preventing accumulated attenuation or changed fade timing. Master remains process-tree CoreAudio attenuation.

## Native settings

Cursor confinement is opt-in and runs on the native helper's UI thread. It requires a visible game and foreground launcher/game HWND, updates with viewport/DPI/movement, releases for settings/blur/hide/minimise/close, and exits if either window is destroyed or the command pipe closes. Windowed clipping uses the launcher client area, including the top menu, with a 12-DIP inset on sides/bottom. Fullscreen uses the game area with that inset on every edge. Bounds are clamped to keep tiny windows valid. Recorded modifier keys toggle on release without swallowing normal chords; F11 and Escape cannot be assigned. Key capture runs only in the local settings dialog and stops on completion/cancel/dismiss/reconnect. Shortcut repeats do not oscillate the setting. Only the shortcut's transient key state is tracked; no text/keystroke history is recorded. The helper does not call SetCursorPos or hide the cursor. Audio COM work runs on a separate MTA thread so slow devices cannot block shortcut processing or cursor release. If another application replaces the clipping rectangle, cleanup does not remove its newer rectangle. Automated tests never call ClipCursor, including on inactive desktops.

Audio attenuation enumerates active Windows render endpoints and applies ISimpleAudioVolume only to sessions whose process IDs belong to the game process tree. It does not modify device master volume, system sounds or another application's session. Actual session levels are read back and exposed as numeric diagnostics; no account data is included. Audio devices and newly created sessions are revisited every second. A game or another mixer can still change its own audio between polls.

Settings are saved atomically in a local profile. A URL change is staged until explicit reconnect. Browser history, tabs and bookmarks are discarded by migration. Existing Flash profile data is retained to preserve sign-in. Paste reads the clipboard only on an explicit game paste; pasted text never crosses the launcher pipe or enters diagnostic logs.

## Native rendering quality

A separate launcher-owned BlitzDisplay class exposes bounded picture zoom and numeric render diagnostics on the reviewed same-origin Flash object. The build validates the existing layout prefix/clamp/clipping instructions and makes same-size substitutions inside Main.method_561. For the reviewed October 10 revision it additionally verifies the full hash of Game.method_1947 and restores exactly 38 bytes of scale-aware transition allocation. The resulting allocator must hash-identically match the historical method. A separately hash-checked 14-byte substitution in class_23.method_1753 rounds the terrain-cache comparison like its allocator, preventing destruction/reallocation on every frame at fractional raster scales. Both corrected bodies are rehashed after SWF serialization. Branch/exception offsets and all other original display-unrelated bodies remain unchanged. Unknown hashes fail the build. DevSettings flags, game clocks, input listeners and packet handlers are unchanged. The game allocates its own higher-resolution bitmap and uses its own cache invalidation. Normal rendering has no capture overlay. Native layout inputs are bounded to 4096×2730; very large requested zoom uses residual browser scaling to preserve magnification without unbounded bitmap allocation. Unknown clients retain the prior safe rendering fallback.

The optional render-resolution preference accepts only 1, 0.75 or 0.5 independently in the shell policy and game command handler. The raster planner retains the same allocation bounds and picture magnification. Full native detail remains the default; lower resolution uses explicit browser magnification of a smaller Flash bitmap. Counter magnification is separately bounded to 0.1–16 in the existing picture-zoom callback. No game frameRate, simulation clock or packet timing is changed. The graphics-acceleration preference is passed as a validated startup boolean to the separate game process; inactive-desktop tests still force software rendering.

BlitzFrameCounter adds one passive ENTER_FRAME observer to Main, after the existing game-loop listener. It uses counted events and unsigned getTimer intervals, updates a small TextField once per second, and makes no frame capture, per-frame IPC or outbound telemetry calls. Low/high history stores at most 31 numeric averages/timestamps, expires samples older than 30 seconds and never stores frame payloads. The TextField is not mouse-enabled, selectable or tab-enabled. Placement includes the original frame border and hides the label when neither gray side fits. The same numeric-only render diagnostic reports sampled frames, elapsed time, cadence and extrema; no account or gameplay state is exposed. Unknown client revisions receive no counter. The fixture's clock and stall controls are absent from the production client delta; host test commands remain unavailable in packaged production launches.

## Packaging and limits

FPS visibility defaults to false in both the settings policy and Flash helper. Only an explicit saved boolean enables it. The shell rejects nonboolean updates, and the host accepts only a boolean show-fps command over its existing authenticated pipe. The revision-pinned helper receives a literal boolean through its same-origin callback; no new network or debugging surface is added. Hiding changes presentation only; the bounded passive observer remains available for numeric diagnostics and retains its rolling range.

The experimental neural enhancer was removed in 0.6.2. Production rendering no longer captures game frames, uploads them to a learned model or creates a second graphics surface. Its native module, model, shaders, command/status handlers and preferences are removed. Build preparation cleans only known retired resources; package verification rejects leftover enhancer files. Original Flash owns the game rendering and input. Test-only game captures remain guarded and never acquire the desktop. The optional offline RIFE research CLI/model stay in ignored .test-tools and never ship.

Modern executable fuses disable RunAsNode, NODE_OPTIONS, command-line inspection and extra file privileges; enable cookie encryption, ASAR integrity and ASAR-only loading. Imported Flash/legacy executable hashes are recorded in runtime/provenance.json. The root launcher verifies the matching versioned executable before starting it. No Windows Authenticode signing certificate is supplied.

## Signed GitHub updates

The packaged shell checks the fixed Daniel-Prizer/dungeon-blitz-launcher GitHub repository after 10 seconds and every six hours. A strict platform/version manifest is verified using the Ed25519 public key shipped with the installed shell. The private key is outside the repository, with access limited to its owner and SYSTEM. GitHub account or release-asset access alone is insufficient to produce an accepted update. Rollbacks, malformed paths, wrong platforms, duplicate paths, unsupported download origins, unsigned releases and mismatched ZIP/file hashes are rejected.

Downloads use HTTPS, bounded redirects/responses, cancellation and signed byte limits. Staging is private to the user/SYSTEM. The native extractor rejects traversal, Windows device paths, duplicate entries, links and excessive expansion. The exact extracted file set is checked before staging, and the native installer rechecks sizes/hashes and rejects reparse points before copying. This does not protect against malware already executing with the user's full Windows privileges.

Only the validated versioned ZIP layout is updated, with a writable-folder preflight. Updates never elevate privileges or request game-controlled executable paths. Hash verification streams files asynchronously. Installation waits for the launcher, game host and native controller to exit, copies into a fresh directory on the destination volume, moves the completed build into its version folder and atomically replaces the root shim, retaining its previous version. The installer never kills those processes. An interrupted shim replacement can retry only when the installed version exactly matches the signed files. Automatic updates are optional; an explicit Install & restart action is also available. No account/profile files are in a signed payload. Older builds without this updater require one manual upgrade.

The imported Adobe runtime is from the user's existing official Dungeon Blitz R installation for local use. Review third-party distribution rights before sharing. An obsolete Flash engine remains a material security limit despite process separation and reduced surface area.

## Experimental widescreen boundary

The preference is strictly boolean and defaults off in the shell and Flash helper. The existing authenticated pipe carries only that validated boolean, forwarded to one same-origin Flash callback. It creates no filesystem, network, external-launch or Node API. Unknown client revisions cannot enable the adapter. The helper uses typed, reviewed client fields rather than arbitrary reflection. It widens Camera.SCREEN_WIDTH only when one Game is in STATE_PLAY; login/menu/handover states restore 1152. It invokes the original resize/cache-invalidation path, including the corrected transition allocator, within the existing raster budget. Camera extent changes are experimental; no game clock, damage/stat formula, authentication or packet handler is edited.

UI offsets use weak-key storage, record Flash's actual rounded positions, avoid unnecessary writes/accumulation, and restore only positions not superseded by the game. Bottom HUD/menu groups retain their original ordering and dimensions. Top controls move through their existing hit-test roots. The noninteractive border uses three clipped instances of the loaded game's original a_EdgeHud vector asset; corners/sides retain their original size and only the horizontal middle extends. No new artwork is downloaded or bundled. Original terrain tile sizes and pool budget remain unchanged; six even half-tile columns cover the wider view and four are restored on exit. There is no captured image overlay, synthetic input forwarding or per-frame IPC. A local post-frame layout listener exists only while the option is enabled. Test-only allocator/world/clock controls are absent from production deltas. Actual terrain-cache/Game drawing regressions cover camera offsets, cache reuse and pixel coverage with a smaller disposable pool; original offline assets and live unauthenticated title tests do not establish authenticated combat performance or every live overlay.

## What protection means against future Flash vulnerabilities

This is a hardened launcher around an unsupported runtime, not a repair of Flash's memory safety. Adobe ended support and security patches after December 31, 2020: [Adobe Flash Player end of life](https://www.adobe.com/products/players/flash-player-distribution.html). The shipped Adobe 32.0.0.363 and Chromium 87 binaries retain known and potentially undiscovered flaws. A version bump or signed update does not itself fix those flaws. For example, the shipped version falls in Adobe's affected range for [CVE-2020-9746, a critical code-execution issue](https://helpx.adobe.com/nz/security/products/flash-player/apsb20-58.html). Origin checks are not a patch for that vulnerability.

| Attack path | Shipped protection | Remaining limit |
| --- | --- | --- |
| Game page reaching privileged shell features | Separate processes, sandboxed renderers, no remote Node/remote module, exact-frame shell IPC, validated commands and origin restrictions | Obsolete native engine bugs can bypass JavaScript/application checks; this is not a demonstrated exploit-proof boundary. |
| Unsolicited navigation/downloads or malicious links | Restricted HTTP origin, downloads denied, user-activated validated external links handed to the default browser | The configured origin can itself serve a malicious SWF. HTTP restrictions do not restrict raw Flash TCP sockets. |
| Corrupt or mismatched client patches | Pinned input/method/output hashes, bounded reconstruction, unknown clients run unchanged | These hashes protect adapter correctness; they do not block unknown Flash content from executing. |
| Tampered GitHub update | Pinned Ed25519 signature, complete file hashes, strict paths/file set, private staging, revalidation before atomic replacement | A stolen signing key or malware with the user's Windows privileges remains a threat. The game SWF is separately served by the game origin. |
| Future Flash code-execution or sandbox-escape CVE | Reduced interfaces and existing Chromium process sandboxing make some attack paths harder | No future-CVE guarantee. A runtime exploit or exploit chain could compromise data or escape containment; no exhaustive penetration test or independent audit establishes otherwise. |

The projector/AppContainer prototype is excluded from release packages because SharedObject persistence currently fails under isolation. Its containment tests are useful evidence for future work, but provide **no protection to the shipped launcher**. AppContainer can restrict process resources using OS-enforced capabilities ([Microsoft's isolation documentation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)); it still requires a working persistence broker, narrow network permissions, and complete rendering/input/link/live-server validation before promotion. Even then it would contain some exploits rather than eliminate Flash CVEs. A dedicated VM with limited host integration would add a separate containment boundary; it is not part of this release.

Accordingly, this build should not be described as secure against arbitrary SWFs or future Flash vulnerabilities. It is designed for a trusted Dungeon Blitz server, with authenticated launcher updates and fewer exposed browser features. Use outside that scope has not been validated.
