# Client audio and upscaling investigation — 9 October 2026

The audio adapter is implemented in 0.4.0. Version 0.6.0 corrects the misleading graphics controls introduced in 0.5.0, adds original/neural comparison and uses a stronger smoothing model. Frame generation was tried offline and remains outside the live launcher.

## Audio

The exact reviewed client SHA-256 is `7f3f40180f5d00f528c99ef7603eebdb89000dbef6ce154e2fb6695deb7c78ae`. Headless FFDec export of that client confirms `SoundManager.SetSoundVolume`, named embedded effects in `SoundManager.Play`, and separately indexed MP3 streams with individual volume controls in `method_218`, `method_103` and `method_748`. The dated 7 October live-source capture additionally identifies the music channel through `Game`'s `dbMusicVolumeInverted` setting, and another streaming channel used by `DayNightManager`.

Master attenuates the game's already mixed Windows audio sessions. The revision-pinned client adapter additionally applies independent Player, Music, Environment and Creatures gains before that mixing, with live updates for existing channels. Entity, ability, combat, projectile and speech sound calls carry their emitter context; room/world calls select Environment, and stream indices separate Music from ambience. A specific mob-water effect has not been identified or tested. `RunWater` and `LandOnWater` are names in SoundConfig; they do not establish which sound a particular enemy emits. Updates cover existing playing/looping channels as well as future playback.

## Live upscaling

The implemented mode uses [CuNNy](https://github.com/funnyplanter/CuNNy), a real learned convolutional model, through a launcher-owned D3D11 adapter. The 4x16 NVL six-pass shader is pinned to revision 906031bb00c15dd6a6bbbaa21c0eb0b724ca8437 and SHA-256 4540ee2bf570b13088451d934ea631f152620c1275f37cf9b9bf607388886c11. It replaces the weakest veryfast model used in 0.5.0. Original source and upstream license notices ship as replaceable local resources. It is not DLSS and does not create intermediate animation frames.

Flash retains its native raster and input surface. Game-only compositor bitmap pixels enter the host's own D3D11 queue, the model reconstructs a 2× texture, and a GPU display pass explicitly fits the result to a window-sized swapchain. An input-transparent nonactivating owned window presents it above the native game HWND. This is smoothing/reconstruction at a fixed window size, not a screen-resolution increase. CPU capture/upload remains; no zero-copy claim is made. Lowering Flash raster resolution was tried and discarded because it softened the source and made private-desktop capture slower. The original stage, zoom, focus cleanup and native input coordinates remain unchanged.

The original 0.5.0 tests inspected a larger intermediate image rather than measuring the final window-sized difference. In 0.6.0, the actual 1280×868 display pass is compared with the exact captured source: about 6% of pixels change by more than six combined RGB levels, but the average per-channel difference is only about 0.46/255. Visual inspection agrees that the effect is small and mostly along edges; this is not evidence of a dramatic quality improvement. The RTX 4080 SUPER executed the quality network and normalization/display passes; sampled GPU times were roughly 1.5–4.3ms, separately from capture delays. Processing remained near 30 captures/s, and a captured image can repeat the same game frame. These GPU/capture timings do not measure input-to-photon latency.

The legacy [FrameSubscriber implementation](https://github.com/electron/electron/blob/v11.5.0/shell/browser/api/frame_subscriber.cc) hardcodes its maximum capture rate to 30. Consequently the 60/120 processing ceiling could not increase subscription output. That selector has been removed and its saved preference is discarded. The API's Done callback explicitly makes an RGBA bitmap; Windows capturePage delivers a BGRA bitmap. Assuming a single ordering caused swapped colors when falling back between paths. An explicit format tag now selects GPU normalization, preserving one RGB interpretation for both. Tests compare real captured PNG colors against the GPU input exactly, including an actual RGBA subscription and a BGRA capturePage frame, rather than checking only synthetic test colors.

An optional hardware-accelerated private-desktop attempt could not obtain a responsive game-renderer capture in the guarded timeout. It is recorded as failed/unestablished, not a passing production-GPU test. The normal software-compositor capture plus real D3D11 neural execution passed. No test controls the input desktop, and physical GPU-compositor presentation, display cadence and authenticated combat remain unverified. Empty or stalled capture now falls back to Original with a Settings note instead of indefinitely claiming a working enhancer.

Original is the default and removes the overlay immediately. Capture failures, allocation/device errors, a two-second capture timeout or a stalled GPU queue restore Original without a popup. Settings hide the game and its owned presentation window; native hit-test/placement/focus tests and live dummy login typing/paste passed under the guard. Physical OS pointer input and desktop scanout are deliberately not tested on Daniel's desktop.

[AMD FSR 1](https://gpuopen.com/fidelityfx-superresolution/) is a real spatial upscaler: its edge-adaptive reconstruction enlarges the input frame, followed by contrast-adaptive sharpening. It does not need motion vectors, depth or frame history. It is a plausible option for a GPU presentation path around the existing Flash renderer. [NVIDIA Image Scaling](https://www.nvidia.com/en-us/geforce/news/nvidia-image-scaler-dlss-rtx-november-2021-updates/) is another spatial scaling solution. Neither is implemented or benchmarked in this launcher.

[DLSS](https://developer.nvidia.com/rtx/dlss) needs engine integration and motion data. This launcher's Flash rendering path does not provide those inputs. [DLDSR](https://www.nvidia.com/en-us/geforce/news/gfecnt/20221/god-of-war-game-ready-driver/) is a different, driver-level technique: render above monitor resolution and downsample. It is not a drop-in upscaling API for this launcher.

A production-grade upscaler still needs wider GPU/vendor/DPI testing, physical presentation latency measurements and authenticated long-session validation. The implemented experiment bounds capture/GPU queues, preserves native input and restores Original on failure. It does not capture the desktop or install a global input hook. Production frames never go through screenshots/PNG/base64 or launcher IPC; the optional offline interpolation experiment uses PNG fixtures and is a separate path.

The control is Image enhancement: Original / Neural smoothing (experimental). Comparison shows the same image with original pixels on the left and the learned/display result on the right, with a thin divider. The original half is verified byte-identical in RGB; native z-order and display-target dimensions are checked in addition to geometry and hit testing. There is no FPS or screen-resolution control. Visual reconstruction may improve or worsen specific text/artwork; invented detail is not recovered original artwork. This mode does not alter multiplayer packets, server state or game animation timing. The captured presentation can lower displayed frame rate versus native Flash and add input delay, so it should not be promoted as a performance feature.

## 60/120 FPS and animation timing

The exact pinned public client starts its stage at 30 FPS and Main.Init changes it to 100 FPS on Flash versions 11 and newer. Therefore describing this game as universally capped at 30 FPS would be incorrect. This is a revision-specific code observation, not measured live combat frame cadence. The launcher does not change either assignment, Game.TARGETFPS, animation timers, physics, sound ticks or network scheduling. Raising a simulation clock to 120 without reviewing those dependencies could change game speed; this release adds no such edit.

[RIFE ncnn Vulkan](https://github.com/nihui/rife-ncnn-vulkan) can estimate intermediate frames from pairs of images without engine motion/depth inputs. It was actually run offline, using the official 20221029 Windows release's rife-v4.6 model on the RTX 4080 SUPER. Its original CLI expects RGB PNG fixtures; supplying RGBA created striped output and was corrected before measuring. No corrupt output is accepted as evidence.

For 96 input frames of a square moving at 8 pixels/frame, the first 720p output positions were approximately 119.5, 123.5, 128.1, 131.5 and 136.1 pixels: inserted images occupy intermediate positions. The source duration (95/60 seconds) equals the output duration (190/120 seconds), both 1.583333 seconds. A 360p repeat passed the same duration and intermediate-motion checks. Interpolation changes display sampling, not simulation speed.

Measured bulk throughput, including model initialization and file decoding/encoding, was about 35 newly inserted frames/s at 720p and 55 at 360p. These numbers do not establish live 60/120 FPS, neural inference latency, or game input lag. Pairwise interpolation normally buffers until the next real frame arrives: at 60 source FPS that alone can add about 16.7ms before compute/capture/display overhead; at 30 it is about 33.3ms. A resident in-memory GPU integration could improve bulk results, but this launcher currently lacks a proven fast frame-acquisition path. Shipping a per-frame CLI/PNG subprocess would be a poor live implementation, so it remains an offline experiment. Neither RIFE binaries nor its models ship.

[AMD frame interpolation](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/frame-interpolation/) expects engine integration inputs that this Flash path does not expose. DLSS frame generation is similarly not a drop-in wrapper. A future live path would need a resident model, bounded timestamped frames, display scheduling and real input latency/artifact measurements, while keeping all game clocks unchanged.

To reproduce the offline experiment, run node scripts/research-frame-generation.cjs --download (about 431MB, extracts only the selected CLI/model into ignored .test-tools), then use .test-tools/PrivateDesktop.exe with the absolute node executable path and absolute scripts/research-frame-generation.cjs path. The helper refuses input-desktop execution and never switches desktops. BLITZ_RIFE_WIDTH=640 selects the 360p run; otherwise it uses 720p. Results are ignored results-640.json/results-1280.json. The official asset supplies no separate publisher checksum; provenance records the URL/release and a locally computed hash, not independently verified integrity.
