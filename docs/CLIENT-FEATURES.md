# Client audio and upscaling investigation — 9 October 2026

The audio adapter remains available. Version 0.6.1 removes the experimental live neural enhancer because its visible benefit was too small for its capture/GPU overhead. Original native Flash rendering is the only shipped path. Neural controls, preferences, modules and models are removed; frame generation remains outside the live launcher.

## Modern browser investigation (12 October 2026)

The new official address is **https://dungeonblitz.theminesa.studio/**, without the `r` in the old hostname. A fresh isolated Edge 155.0.4283.45 context renders its actual class-selection artwork into a 1440×900 canvas, with one Ruffle player and no Flash-required fallback. The old `dungeonblitzr` page still requires Flash. Both origins serve the same current game bytes: `swf-c93b05a5cf72`, SHA-256 `fa4e3a9ba72eb6394cde3cc40b98e918a8c581b7d7b126e1d7a1f81c0017fc12`, 934,243 compressed bytes.

The page configures Ruffle with a secure WebSocket proxy from the game's original `dungeonblitzr.theminesa.studio:8080` socket to `wss://dungeonblitzr.theminesa.studio/game-ws`, and rewrites legacy HTTP asset URLs to the new origin. This is a server-provided bridge; the launcher should not invent another local TCP proxy. Reading that configuration does not establish successful authenticated multiplayer.

The served engine identifies itself as **local 0.7.1**, built **2026-10-12T16:49:53.895Z**, with commit metadata `6764838a482064d5729145e716bf389fc39269b3`. That commit URL is not available in the upstream public repository, so these identifiers do not prove source provenance or a clean upstream build. The current upstream `readGraphicsData` implementation remains a stub, but the **actual served build returns three graphics-data entries** for a filled rectangle and renders the expected pixel through `BitmapData.drawWithQuality`. The earlier upstream API finding therefore does not rule out this custom engine.

`npm run check:modern-enhancements` loads our prepared native-controller/original-asset fixture under that served engine in a separate headless context. The fixture uses no account, all sockets are blocked, and only the exact fixture assets and official Ruffle files are permitted. It verifies ExternalInterface callbacks, native-size rasters, aligned cached NPC text at five scales, the 16:9 frame and cached expanded HUD, centered native hotbar restoration, inspection-mode decoration, and actual original Home artwork through the game renderer/cache. Captured fixture screens were inspected. Synthetic state includes empty/default ability slots and menu data; those are not evidence of a populated live game. Autoplay warnings are expected without a user gesture, and audible audio was not tested.

**Recommendation:** develop a modern Ruffle host using the current isolated Electron renderer, retaining the launcher shell and reviewed client hooks. The successful callback/HUD probe means the enhancements need not be discarded. Removing the legacy Electron/Adobe plugin would remove that obsolete runtime dependency; it would not guarantee immunity to vulnerabilities or improve combat FPS by itself. The installer, signed updater, settings, titlebar and window policy can remain. Process audio, key routing, cursor ownership and renderer attachment need revalidation with the new process model.

Before enabling a production replacement:

1. Establish the custom engine's source/license provenance, pin its tested JS/WASM resources and retain bounded origin/permission/link policies. Do not silently trust every future engine replacement or load remote Node APIs.
2. Privately verify real characters, animation/artwork, zones, combat, map input and all loading/menu states through the official WebSocket bridge. Avoid concurrent account sessions. Confirm original clocks/packets and compare full-session frame cadence/input delay; a software-rendered fixture is not a combat benchmark.
3. Test isolated Ruffle SharedObject persistence and an explicit saved-login handoff. Adobe's profile and the new origin's browser storage are different. Do not decode/copy credentials into notes or assume the existing Flash sign-in automatically transfers.
4. Verify master/category sound, mute/unmute, Shift mounting, clipboard/chat focus, Escape/fullscreen, DPI/detail/zoom, crash/close cleanup and update installation under the modern host. Keep the established host available until these checks pass.

Run `npm run check:modern-web` for the new public page, or pass the old URL to compare. Run `npm run test:camera` first to prepare the fixture, then `npm run check:modern-enhancements`. Reports and screenshots remain ignored under `docs/modern-web-check/`; imported game/engine files and account data are not release assets. The public-page probe blocks local bridges, Discord auth/presence and non-GET/HEAD requests. Neither probe logs in. No production runtime migration is included in 0.20.0.

## Audio

The exact reviewed client SHA-256 is `7f3f40180f5d00f528c99ef7603eebdb89000dbef6ce154e2fb6695deb7c78ae`. Headless FFDec export of that client confirms `SoundManager.SetSoundVolume`, named embedded effects in `SoundManager.Play`, and separately indexed MP3 streams with individual volume controls in `method_218`, `method_103` and `method_748`. The dated 7 October live-source capture additionally identifies the music channel through `Game`'s `dbMusicVolumeInverted` setting, and another streaming channel used by `DayNightManager`.

Master attenuates the game's already mixed Windows audio sessions. The revision-pinned client adapter additionally applies independent Player, Music, Environment and Creatures gains before that mixing, with live updates for existing channels. Entity, ability, combat, projectile and speech sound calls carry their emitter context; room/world calls select Environment, and stream indices separate Music from ambience. A specific mob-water effect has not been identified or tested. `RunWater` and `LandOnWater` are names in SoundConfig; they do not establish which sound a particular enemy emits. Updates cover existing playing/looping channels as well as future playback.

## Native rendering correction in 0.6.3

The fixed 1152×768 layout patch in earlier releases kept the game bitmap around 1062×616, while Chromium page zoom enlarged it to fit the window. This enlarged already-rasterized edges. The revised exact-hash adapter retains actual stage dimensions, applies picture zoom inside Flash, removes only the obsolete 1.25 raster-size assignment, and clips against the full real stage. The original resize/cache-invalidation method now allocates a larger bitmap. No original method outside the reviewed layout is changed by the display builder. Normal 1080p/1440p uses browser zoom 1 at 100% Windows DPI; the host compensates density and bounds exceptionally large zoom layouts.

Real same-window old/native captures measured 1062×616 versus 1494×867 at 1920×1080 and 1998×1159 at 2560×1440. That is about 1.98× and 3.54× the old game-bitmap pixels. Full artwork, text and all class characters remain visible; inspected captures show cleaner edges. The measured animation rate remains 100 before and after. This is a native raster correction, not generated detail or a frame-rate feature. Tests use the guarded inactive desktop and never log in. Other monitor/DPI configurations and authenticated long sessions remain outside these measurements.

The reviewed SuperAnimData and Game drawing calls explicitly select StageQuality.HIGH, which provides native 4×4 antialiasing according to the [StageQuality reference](https://airsdk.dev/reference/actionscript/3.0/flash/display/StageQuality.html). These calls remain intact. A global quality label would not override their explicit setting. Rendering the original artwork directly at the required pixel size avoids the previous extra enlargement step; no sharpening, color adjustment or generated-detail filter is added. This is the cleanest path demonstrated by these captures, not a claim of an exhaustive comparison with every possible scaler.

[Flash Browser v0.81 source](https://github.com/radubirsan/FlashBrowser/blob/e113aa4/index.js) also initializes page zoom to 1. It was inspected for comparison; the friend’s computer and an authenticated Flash Browser combat session were not tested.

## Cached artwork origins in 0.16.0

The reviewed SuperAnimData crop transform incorrectly translated logical coordinates by a pixel crop offset. The separate display helper now transforms that offset through the inverse matrix before translating, preserving both scale axes and rotation/shear terms. Exact original method hashes and serialized corrected bytes are checked for every supported client; all unrelated methods stay unchanged. The isolated original baseline reproduces shifted real NPC text, while corrected cached and direct-vector bounds match at five scales. The existing high-quality native drawing calls, raster budget, original game clocks and input remain intact.

## Removed neural enhancement: historical results

Versions 0.5.0 and 0.6.0 tried [CuNNy](https://github.com/funnyplanter/CuNNy), a learned model, through a launcher-owned D3D11 overlay. The stronger six-pass 4x16 model reconstructed a 2× texture then fitted it to the same window size. The final display changed roughly 6% of pixels by more than six combined RGB levels, but the average per-channel difference was only about 0.46/255. This did not demonstrate a worthwhile visible upgrade.

The pinned [Electron 11 FrameSubscriber](https://github.com/electron/electron/blob/v11.5.0/shell/browser/api/frame_subscriber.cc) capped capture at 30/s. The earlier 60/120 selector could not overcome it or create new game frames. Capture and uploads could reduce displayed smoothness and add delay. GPU samples of roughly 1.5–4.3ms on an RTX 4080 SUPER were not end-to-end input latency. Hardware-accelerated capture on the inactive test desktop timed out; physical GPU presentation was not established.

Same-frame comparisons and explicit RGBA/BGRA normalization proved that the stronger model did process pixels; the original half matched the source exactly. These results and the user feedback support removing the entire enhancer, rather than adding more overhead for an unproven quality increase. No neural module, model or overlay ships in 0.6.1. Game zoom and all original game clocks remain unchanged. The historical source is available in Git history.

## Interaction-delay investigation in 0.6.4

The user reported delayed NPC clicks followed by queued actions. The cause has not been reproduced. The reviewed client limits interaction attempts to intervals of at least 50ms and sends a talk-to-NPC packet for nonlocal levels; this is client-code evidence, not a measurement of Minesa server response time. No click debouncing, packet cadence, input listeners or game clocks are changed.

The separate legacy Chromium game window now disables native occlusion heuristics in production, as the isolated tests already did. This avoids a possible embedded-window backgrounding cause while preserving the explicit background-activity setting. A [Chromium developer's explanation of native Windows occlusion](https://groups.google.com/a/chromium.org/g/embedder-dev/c/ZF3uHHyWLKw) describes stopping rendering for covered windows and contention from Windows event tracking. Applying that to this launcher's separate game/owner windows is an inference; it is not proof of the reported delay's cause or a verified fix.

On the inactive, software-rendered desktop, 24 sequential probes per case each measured three renderer/Flash diagnostic calls. At 1920×1080, old/native median durations were 20.7/33.4ms, p95 31.2/43.2ms and maximum 33.4/63.2ms. At 2560×1440 they were 51.3/52.5ms, p95 64.4/67.2ms and maximum 64.6/67.9ms. No multi-second title-screen stall appeared. These figures are neither input latency nor achieved FPS; they exclude authenticated combat, physical GPU presentation and server response timing. Native sizing increases raster work, and no performance improvement is established.

## 60/120 FPS and animation timing

### Passive counter and CPU raster budget in 0.7.0 / 0.8.0

The counter observes the same Main ENTER_FRAME event source as the game loop, counts delivered events over actual unsigned getTimer intervals, and updates text once per second. An initial stage EXIT_FRAME prototype overcounted events compared with the game source and was discarded. The shipped listener is passive and runs after the existing game listener; it changes no clocks, packets or game bytecode. See the primary [Flash frame-event reference](https://airsdk.dev/reference/actionscript/3.0/flash/events/Event.html#ENTER_FRAME) and [getTimer reference](https://airsdk.dev/reference/actionscript/3.0/flash/utils/package.html#getTimer()). This is game-loop cadence, not unique artwork frames or GPU presentation.

A 1.5-second read-only sample of the existing game process found one Flash plugin thread using about 96.4% of one logical processor on a 32-logical-processor system. One saturated thread represents only about 3.1% of that CPU's total logical capacity. This is evidence of a busy Flash thread during that short sample, not proof of a particular combat scene's bottleneck. No desktop, game credentials or account state was inspected.

The optional 75%/50% render resolution reduces the bitmap dimensions while retaining displayed picture size through bounded browser magnification. It deliberately trades sharpness for fewer pixels; default 100% retains the sharp native path. At 1440p, actual bitmaps measured 1998×1159 (100%), 1494×867 (75%) and 996×578 (50%). At 1080p they measured 1494×867, 1122×651 and 744×432. The picture's displayed scale stayed within 0.5%, the counter's physical size stayed equal, and the game's target remained 100 at every setting. Three title-screen frame samples per setting were approximately 59–61 FPS on the inactive software-rendered desktop. This did not demonstrate an FPS gain; authenticated combat, physical GPU scanout and server delays remain outside the measurements.

The existing graphics-acceleration checkbox now reaches the separate game host at startup too. It does not rewrite the game's ActionScript or draw path to offload additional work to the GPU. No process-priority, CPU-affinity, global graphics or unsupported renderer switches are added.

Version 0.8.0 displays Low and High alongside current FPS. They are extrema of measured averages ending within the last 30 seconds, not individual frame times or percentile lows. History is bounded to 31 samples and allocates only at the approximately once-per-second update; existing unsigned-clock arithmetic is retained. The counter does not alter game scheduling. Version 0.9.0 adds Settings → Display → Show FPS counter, off by default for new and migrated profiles. Changes apply immediately and persist; hiding only affects the label, retaining the passive numeric diagnostic and recent range.

The single-thread bottleneck has not been fixed. ActionScript can support [Workers](https://airsdk.dev/reference/actionscript/3.0/flash/system/Worker.html) for selected parallel work, but their isolation and restricted UI access mean the existing game loop cannot simply be spread across cores by a launcher setting. Offloading suitable work would require engine/client restructuring, profiling and multiplayer regression testing. This release only reduces optional drawing work and observes actual frame cadence.

The exact pinned public client starts its stage at 30 FPS and Main.Init changes it to 100 FPS on Flash versions 11 and newer. Therefore describing this game as universally capped at 30 FPS would be incorrect. This is a revision-specific code observation, not measured live combat frame cadence. The launcher does not change either assignment, Game.TARGETFPS, animation timers, physics, sound ticks or network scheduling. Raising a simulation clock to 120 without reviewing those dependencies could change game speed; this release adds no such edit.

[RIFE ncnn Vulkan](https://github.com/nihui/rife-ncnn-vulkan) can estimate intermediate frames from pairs of images without engine motion/depth inputs. It was actually run offline, using the official 20221029 Windows release's rife-v4.6 model on the RTX 4080 SUPER. Its original CLI expects RGB PNG fixtures; supplying RGBA created striped output and was corrected before measuring. No corrupt output is accepted as evidence.

For 96 input frames of a square moving at 8 pixels/frame, the first 720p output positions were approximately 119.5, 123.5, 128.1, 131.5 and 136.1 pixels: inserted images occupy intermediate positions. The source duration (95/60 seconds) equals the output duration (190/120 seconds), both 1.583333 seconds. A 360p repeat passed the same duration and intermediate-motion checks. Interpolation changes display sampling, not simulation speed.

Measured bulk throughput, including model initialization and file decoding/encoding, was about 35 newly inserted frames/s at 720p and 55 at 360p. These numbers do not establish live 60/120 FPS, neural inference latency, or game input lag. Pairwise interpolation normally buffers until the next real frame arrives: at 60 source FPS that alone can add about 16.7ms before compute/capture/display overhead; at 30 it is about 33.3ms. A resident in-memory GPU integration could improve bulk results, but this launcher currently lacks a proven fast frame-acquisition path. Shipping a per-frame CLI/PNG subprocess would be a poor live implementation, so it remains an offline experiment. Neither RIFE binaries nor its models ship.

[AMD frame interpolation](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/frame-interpolation/) expects engine integration inputs that this Flash path does not expose. DLSS frame generation is similarly not a drop-in wrapper. A future live path would need a resident model, bounded timestamped frames, display scheduling and real input latency/artifact measurements, while keeping all game clocks unchanged.

To reproduce the offline experiment, run node scripts/research-frame-generation.cjs --download (about 431MB, extracts only the selected CLI/model into ignored .test-tools), then use .test-tools/PrivateDesktop.exe with the absolute node executable path and absolute scripts/research-frame-generation.cjs path. The helper refuses input-desktop execution and never switches desktops. BLITZ_RIFE_WIDTH=640 selects the 360p run; otherwise it uses 720p. Results are ignored results-640.json/results-1280.json. The official asset supplies no separate publisher checksum; provenance records the URL/release and a locally computed hash, not independently verified integrity.
